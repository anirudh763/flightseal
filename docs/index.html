Interpretation

A file integrity result and an external trust conclusion answer different questions. A pass means this file matches its own hash chain and, with receipts, what a witness was sent while it was written.

It does not show the data was true when it was sealed, or that every byte of the original flight log was kept.

      Trust help
      
        
      What each result means, what it does not mean, and the limits of this check.
      
        
      Verdicts
      
        
      
          
      Tampered
      
          
      The hash chain breaks at a record, or a receipt signed by the key you trust does not match the log. A rewritten log and a log whose end was removed look the same to a receipt as receipts that belong to another log sealed with the same key; the page says both.
      
          
      Intact
      
          
      Every record passes its checksum, sequence and link checks, and every receipt signed by the key you trust matches. Records written after the last receipt are named as not covered.
      
          
      UNVERIFIED
      
          
      The chain is consistent (or only the last record is cut short) but the receipts are not evidence: they name another key, their signature does not verify, or this browser cannot check Ed25519. Findings then starts with "UNVERIFIED:", and the text report says RESULT: UNVERIFIED or leaves the receipts NOT CHECKED, as the CLI does.
      
          
      Incomplete
      
          
      The last record is cut short, as a crash while writing leaves it. fseal recover trims only that record.
      
        
      
        
      What a pass means
      
        
        
          
      • Checks run in order for every record: checksum (CRC-32), sequence number, then the SHA-256 link to the record before. Verification stops at the first failure, as fseal verify does.
        • 
          
      • A hash chain pinpoints the first record where the chain breaks, not every altered record. Records after the break are not checked.
        • 
          
      • Truncation of the tail is only caught with receipts. So is a log that its holder rebuilt from scratch: a receipt kept by someone else, signed by the drone's key, pins how the log looked when the receipt was issued. A receipt that does not match shows that something changed between it and the previous matching receipt, not which record.
        • 
          
      • Receipts count only when their signature verifies with the key you trust. If this browser cannot check Ed25519 signatures, receipts are shown as not authenticated: neither proof of tampering nor of integrity.
        • 
          
      • Nothing here shows the data was true when it was sealed (a spoofed sensor looks normal), and records written after the last receipt are not protected. See the threat model.
        • 
          
      • The PX4 converter seals selected decoded ULog records, sorted by timestamp, after the log was downloaded; it does not preserve or authenticate every byte of the original .ulg file, or anything that happened before sealing. See the PX4 ULog specification.
        • 
          
      • Keeping receipts with a separate witness is an operational assumption: the CLI writes receipts to a local file, and the protection holds only if someone other than the log's holder keeps a copy.
        • 
          
      • The tests use one real PX4 flight log (a public pyulog fixture); the browser examples are a synthetic 800-record flight and 2,422 records selected from that PX4 log, with no position or GPS topics.
        • 
          
      • FlightSeal is a narrow, documented workflow to support experiments. It is not proof of safe flight or of an accident's cause, and it is not a reproduction of RVFuzzer or PGFuzz. No user or field validation has been done.
        • 
        
      
        
      Limits of this page
      
        
        
          
      • A receipts file over 16 MB is not read here; use the CLI.
        • 
          
      • Up to 2,000,000 records are listed; every record is verified however many there are.
        • 
          
      • A receipt count with more than 20 significant digits, or above 264−1, is "not a receipt", reported with its line number, before any big-number arithmetic runs.
        • 
          
      • After a record length that runs past the end of the file, at most 16 possible starts of the next record get a full checksum (the same cap as the C++ and Python readers), so a crafted file cannot make the check slow.
        • 
          
      • Verification runs in a background worker; Cancel stops it while the log is scanned and while receipt signatures are checked, and no verdict is shown after Cancel.
        • 
        
      
        
      The verifier is plain JavaScript using your browser's WebCrypto for SHA-256 and Ed25519; its tests require it to print the same report as the C++ CLI on every attack the project tests (when the browser can check signatures). Matching the CLI cannot catch a mistake both share. Built with AI assistance (Claude); see the README. Type uses your system's sans-serif and monospace fonts.
